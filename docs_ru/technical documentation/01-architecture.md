# 01. Архитектура

## Один процесс, три HTTP-приложения

Приложение запускает три независимых экземпляра Fiber на разных портах. Разделение
не косметическое: у каждого слушателя своя модель аутентификации и свои требования
к TLS, совместить их в одном порту невозможно.

| Приложение | Порт (конфиг) | Протокол | Аутентификация | Назначение |
|---|---|---|---|---|
| **UI + API** | `app.port` (43000) | по `app.protocol` | Сессии (UI), API-ключ (`/api/v1/*`) | Веб-интерфейс и REST API |
| **CRL + OCSP** | `app.crl_port` (8080) | по `app.crl_protocol` | нет | Публикация CRL, ответы OCSP |
| **EST** | `app.est_port` (43001) | всегда TLS | Basic Auth и mTLS | Протокол EST (RFC 7030) |

### Почему CRL и OCSP отдельно и по HTTP

RFC 5280 §4.2.1.13 и RFC 5019 §5 предполагают доступ к точкам проверки отзыва по
обычному HTTP. Если бы CDP и AIA указывали на HTTPS, возникла бы циклическая
зависимость: чтобы проверить сертификат, клиенту нужно установить TLS-соединение,
для которого требуется проверить сертификат. Поэтому слушатель отдельный и по
умолчанию нешифрованный - данные там подписаны CA и в конфиденциальности не нуждаются.

### Почему EST отдельно

`simplereenroll` аутентифицирует клиента по ранее выданному сертификату, то есть
требует mTLS. Клиентский сертификат запрашивается на этапе TLS-рукопожатия, когда
сервер ещё не знает URL запроса, - включить mTLS «только для одного маршрута»
нельзя. Поэтому EST живёт на своём порту с `tls.VerifyClientCertIfGiven`, а UI
на основном порту работает без запроса клиентских сертификатов.

Подробности - [08-est.md](08-est.md).

## Порядок запуска

[`main.go`](../../main.go) выполняет строго последовательные шаги:

1. **Конфигурация.** Если рядом с исполняемым файлом нет `config.yaml`, он создаётся
   из встроенного `configInit.yaml` (`//go:embed`). Затем читается через viper.
2. **Логирование.** `utils.SetupSlogLogger()` настраивает `slog` по секции `logging`.
3. **База.** Открывается SQLite, создаются каталоги `db`, `root_ca_tlss`, `https`,
   `crlFile`, `logs`.
4. **Схема.** Выполняются все `CREATE TABLE IF NOT EXISTS` из пакета `models`, затем
   идемпотентные миграции `ALTER TABLE` (см. [03-database.md](03-database.md)).
5. **Мастер-ключ.** Если таблица `secret_key` пуста - генерируется 32-байтный ключ,
   шифруется паролем администратора и сохраняется. Иначе расшифровывается и остаётся
   в памяти процесса в `crypts.AesSecretKey.Key` на всё время работы.
6. **SSH-ключ.** При отсутствии создаётся ключ `Default` для подключения к серверам.
7. **Sub CA в память.** `crypts.ExtractCA.ExtractSubCA(db)` кэширует активный Sub CA.
8. **Фоновые задачи** (пять горутин, см. ниже).
9. **Слушатели.** CRL/OCSP и EST поднимаются в горутинах, UI-приложение блокирует
   главную горутину.

## Фоновые задачи

| Горутина | Интервал из конфига | Что делает |
|---|---|---|
| `check.Monitore` | `monitor.*` | Следит, что остальные чекеры живы |
| `crl.StartCombinedCRLGeneration` | `CAcrl.updateInterval` | Периодически перегенерирует CRL |
| `checkTCP.TCPPortAvailable` | `checkServer.*` | Проверяет доступность серверов по TCP |
| `check.CheckValidCerts` | `certsValidation.*` | Пересчитывает `days_left`, помечает истёкшие |
| `check.RecreateCerts` | `recreateCerts.*` | Перевыпускает истёкшие с флагом `recreate` |

Подробности - [10-checkers.md](10-checkers.md).

## Связи между компонентами

```
                          ┌──────────────┐
                          │  config.yaml │
                          └──────┬───────┘
                                 │ viper
                    ┌────────────┴─────────────┐
                    ▼                          ▼
            ┌──────────────┐          ┌─────────────────┐
            │  controllers │          │  check (чекеры) │
            └───────┬──────┘          └────────┬────────┘
                    │                          │
                    ▼                          ▼
            ┌───────────────────────────────────────┐
            │              crypts                   │
            │  ExtractCA (кэш Sub CA), Aes (ключи)  │
            └───────┬──────────────────────┬────────┘
                    │                      │
        ┌───────────┴─────┐         ┌──────┴──────┐
        ▼                 ▼         ▼             ▼
   ┌─────────┐      ┌─────────┐ ┌───────┐   ┌──────────┐
   │  crl    │      │  ocsp   │ │ models│   │  SQLite  │
   └─────────┘      └─────────┘ └───────┘   └──────────┘
```

Ключевые узлы связности:

- **`crypts.AesSecretKey.Key`** - мастер-ключ в памяти. Без него нельзя расшифровать
  ни один приватный ключ, поэтому от него зависят выпуск сертификатов, CRL, OCSP и
  доставка по SSH.
- **`crypts.ExtractCA`** - кэш активного Sub CA (сертификат + ключ). Заполняется при
  старте и **сбрасывается** при пересоздании Sub CA в `GenerateRSASubCA`. Без сброса
  новые сертификаты подписывались бы устаревшим ключом.
- **`models`** - единственное место, где описаны SQL-схемы; все пакеты используют
  одни и те же структуры для маппинга.

## Хранение и шифрование

Всё состояние - в одном файле SQLite (`database.path`). Приватные ключи всех
сертификатов, пароли контейнеров PKCS#12 и приватные SSH-ключи лежат в базе
зашифрованными AES-256-GCM на мастер-ключе. Сам мастер-ключ хранится в `secret_key`
зашифрованным паролем администратора, который выводится через PBKDF2.

Следствие: **файл базы без пароля администратора бесполезен** - из него нельзя
извлечь ни одного приватного ключа. Но и восстановление невозможно: потеря пароля
означает потерю всех ключей.

Подробности - [04-crypto.md](04-crypto.md).
