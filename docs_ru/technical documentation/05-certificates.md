# 05. Жизненный цикл сертификатов

Три типа конечных сертификатов, у каждого своя таблица и свой набор контроллеров,
но общий набор состояний и общий механизм отзыва.

| Тип | Таблица | Привязка | Контроллеры |
|---|---|---|---|
| Серверный | `certs` | к записи `server` | `serverCertControllers` |
| Клиентский | `user_certs` | к записи `entity` | `usersCertControllers` |
| EST | `est_certs` | к записи `est_users` | `estControllers` |

## Состояния

```
        выпуск
          │
          ▼
    ┌──────────┐   истёк срок    ┌───────────┐
    │ 0 valid  │ ──────────────> │ 1 expired │
    └────┬─────┘   (чекер)       └─────┬─────┘
         │                             │ recreate = 1
         │ отзыв                       ▼
         │                       перевыпуск → 0 valid
         ▼
    ┌────────────┐   откат
    │ 2 revoked  │ ─────────> 0 valid или 1 expired
    └────────────┘            (в зависимости от days_left)
```

Переход в `expired` выполняет чекер `CheckValidCerts`, перевыпуск - `RecreateCerts`
(только если у записи установлен флаг `recreate`). Отзыв и откат инициирует
пользователь через UI.

## Выпуск

Общая схема одинакова для всех типов, отличается только таблица и набор полей:

1. Контроллер валидирует вход: алгоритм из списка (`RSA`, `ECDSA`, `ED25519`),
   допустимая длина ключа, заполненность обязательных полей.
2. Вызывается генератор по алгоритму - например, `crypts.GenerateRSACertificate`.
3. Генератор создаёт ключевую пару и 128-битный случайный серийный номер.
4. Собирается шаблон `x509.Certificate`: Subject, SAN, KeyUsage/EKU по типу
   сертификата, CDP и AIA (см. [04-crypto.md](04-crypto.md)).
5. Определяется подписант: при `SigningCAId = 0` берётся кэш `ExtractCA`, иначе -
   `ExtractExtCA(db, SigningCAId)`.
6. `x509.CreateCertificate` подписывает; приватный ключ и пароль контейнера
   шифруются мастер-ключом.
7. Запись сохраняется в транзакции.

Для серверных сертификатов при включённом `SaveOnServer` дополнительно выполняется
доставка по SSH - если сервер помечен `offline`, контроллер отклоняет запрос заранее.

### Выбор подписывающего CA

В формах выпуска есть поле **Signing CA**: «Core CA» (значение `0`) или одна из групп
внешних CA (значение `entity_ca.id`). Выбор сохраняется в колонке `signing_ca_id` и
определяет дальнейшее поведение - какой ключ подписывает, попадёт ли сертификат в CRL
и какой CA будет отвечать по OCSP.

## Пересоздание

Два разных механизма, которые легко спутать:

### Автоматическое - по истечении срока

Чекер `RecreateCerts` раз в `recreateCerts.recreateCertsInterval` выбирает записи с
`cert_status = 1 AND recreate = 1` и вызывает `Recreate*Certificate`. Функция
генерирует новый ключ и сертификат и **обновляет существующую строку** по `id` -
серийный номер меняется, `id` сохраняется.

Флаг `recreate` задаётся при создании сертификата переключателем в форме.

### Каскадное - при пересоздании CA

Инициируется из UI отзывом Root или Sub CA. Последовательность в
`RevokeCACertWithData`:

1. Текущий CA помечается отозванным, все подписанные им сертификаты - тоже.
2. Удаляются ранее отозванные и истёкшие записи.
3. Генерируется новый CA - при этом сбрасывается кэш `ExtractCA`.
4. Все валидные сертификаты перевыпускаются под новый CA: серверные, клиентские и
   EST с `signing_ca_id = 0`. Обработка идёт пулом горутин с мьютексом на запись в БД.
5. Перегенерируется CRL.

Сертификаты внешних CA в каскад не попадают - они не зависят от нашей иерархии.

## Отзыв и откат

**Отзыв** проставляет `cert_status = 2`, время в `data_revoke`, причину в
`reason_revoke`, после чего сразу перегенерирует CRL.

**Откат** (`Rollback`) возвращает сертификат в оборот: очищает поля отзыва и
выставляет `cert_status = 0` или `1` в зависимости от `days_left`. CRL также
перегенерируется - запись из списка исчезает.

Критично, что `crl.CombinedCRL(db)` вызывается **после** `tx.Commit()`. Генератор
открывает собственные соединения к SQLite и незакоммиченную транзакцию не увидит -
при вызове до коммита в CRL попадёт прежний статус.

## Выгрузка

`TakeCert` (серверные и клиентские) и `TakeESTCert` отдают три формата:

| Формат | Содержимое |
|---|---|
| `zip` | сертификат `.pem`, ключ `.key`, цепочка Sub CA и Root CA |
| `pkcs12` | контейнер `.p12`, современное шифрование |
| `pkcs12-legacy` | контейнер `.p12`, старый алгоритм - для macOS и старого ПО |

Пароль контейнера PKCS#12 - тот, что задан при выпуске; он хранится в базе
зашифрованным и расшифровывается только в момент выгрузки.

Для сертификатов, выпущенных внешним CA, цепочка в архив не кладётся: приложение
не обязано хранить полную иерархию чужого CA.

## Проверка

```bash
# Профиль и расширения
sqlite3 db/database.db "SELECT public_key FROM certs ORDER BY id DESC LIMIT 1;" \
  | openssl x509 -noout -text | less

# Статусы по всем таблицам
sqlite3 db/database.db "
  SELECT 'certs' t, cert_status, COUNT(*) FROM certs GROUP BY cert_status
  UNION ALL SELECT 'user_certs', cert_status, COUNT(*) FROM user_certs GROUP BY cert_status
  UNION ALL SELECT 'est_certs', cert_status, COUNT(*) FROM est_certs GROUP BY cert_status;"

# Сверка статуса отзыва между базой, CRL и OCSP
./tests/revocation/test_revocation.sh <SERIAL>
```
