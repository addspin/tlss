# 02. Подготовка к продовой среде

Конфигурация по умолчанию рассчитана на быстрый старт и локальную проверку. Перед
реальной эксплуатацией её нужно привести в порядок - ниже перечислено, что именно и
почему.

## Обязательно изменить

### `login.authConfig` - убрать пароль из файла

```yaml
login:
  authConfig: false   # было true
```

При `true` логин и пароль читаются из `config.yaml` - то есть лежат на диске открытым
текстом рядом с базой. При `false` приложение спрашивает их в консоли при каждом
запуске, и в файле их нет.

Учтите: с `authConfig: false` автоматический перезапуск потребует ручного ввода.
Если приложение запускается как сервис, придётся выбирать между удобством и хранением
пароля на диске - компромисса здесь нет.

### `app.hostname` - реальное имя

```yaml
app:
  hostname: pki.example.com
```

Используется как адрес привязки всех трёх слушателей и должен совпадать с именем в
серверном сертификате, иначе клиенты будут отвергать соединение.

### `app.protocol` и TLS-сертификат

```yaml
app:
  protocol: https
  certFile: https/pki.example.com.pem
  keyFile: https/pki.example.com.key
```

По умолчанию интерфейс стартует по HTTP. Для продовой среды нужен HTTPS: через
интерфейс проходят пароли контейнеров и приватные ключи.

Эти же файлы использует EST-сервер. Если они не заданы, EST не поднимется - в лог
уйдёт предупреждение.

### Адреса CRL и OCSP

```yaml
CAcrl:
  subCACrlURL: http://pki.example.com:8080/api/v1/crl/subca/pem
  rootCACrlURL: http://pki.example.com:8080/api/v1/crl/rootca/pem

CAocsp:
  url: http://pki.example.com:8080/ocsp
```

Эти адреса **встраиваются внутрь каждого выпускаемого сертификата** (расширения CDP и
AIA) и должны быть доступны клиентам ровно в том виде, в каком записаны. Менять их
после выпуска бессмысленно: в уже выданных сертификатах останется прежнее значение.

Поэтому адреса стоит привести в порядок **до** создания CA и выпуска сертификатов.

Оставьте здесь **HTTP, а не HTTPS**: чтобы проверить сертификат, клиент должен скачать
CRL или получить OCSP-ответ, а если для этого потребуется TLS-соединение, возникнет
циклическая зависимость. Данные подписаны CA и в шифровании не нуждаются.

### Пароль и соль

```yaml
login:
  password: ...
  salt: ...
```

Значения из шаблона конфигурации - примеры. Даже при `authConfig: false` стоит убедиться,
что в файле не осталось значений по умолчанию.

## Стоит пересмотреть

### Интервалы фоновых задач

Значения по умолчанию заданы в секундах и рассчитаны на демонстрацию - в продовой
среде такая частота создаёт лишнюю нагрузку:

```yaml
checkServer:
  unit: seconds
  checkServerInterval: 10        # → minutes, 1-5

certsValidation:
  unit: seconds
  certsValidationInterval: 30    # → minutes, 10-30

recreateCerts:
  unit: seconds
  recreateCertsInterval: 5       # → minutes, 5-15
```

Интервалы монитора (`monitor.*`) задают, как часто проверяется живость чекеров.
Их имеет смысл держать чаще, чем сами чекеры, но также перевести в минуты.

Важно: пороги «чекер не отвечает» вычисляются из настроек самих чекеров, поэтому при
увеличении интервала чекера порог растёт автоматически - отдельно править ничего не нужно.

### Период обновления CRL

```yaml
CAcrl:
  unit: hours
  updateInterval: 24
```

Значение попадает в поле `nextUpdate` внутри CRL: клиенты будут считать список
действительным ровно этот срок. Сутки - разумный баланс. Уменьшать до часов стоит,
только если отзывы происходят часто и важна скорость их распространения.

Помните, что CRL перегенерируется **сразу** при каждом отзыве и откате, так что
интервал влияет лишь на плановое обновление.

### Срок жизни OCSP-ответа

```yaml
CAocsp:
  responseValidity: 24   # часы
```

Определяет `nextUpdate` в ответе и время кэширования на прокси. Чем меньше значение,
тем быстрее клиенты узнают об отзыве, но тем выше нагрузка на респондер.

### Срок сертификатов, выдаваемых по EST

```yaml
est:
  cert_ttl_enrollment: 365
```

Применяется к первичной выдаче через `simpleenroll`. Для устройств, которые обновляют
сертификат автоматически, разумно ставить короткий срок - 90 дней и меньше.

### Логирование

```yaml
logging:
  level: info      # debug только для отладки
  format: json     # удобнее для сбора логов
  output: both     # stdout + файл
  file: logs/tlss.log
```

Ротация логов не встроена - при `output: file` или `both` настройте `logrotate` или
аналог, иначе файл будет расти без ограничений.

## Эксплуатация

**Резервные копии.** Копируйте `db/database.db` и `config.yaml`. Без пароля
администратора восстановить данные из базы невозможно, поэтому пароль храните
отдельно и надёжно.

**Доступ к базе.** Файл содержит все приватные ключи, пусть и зашифрованные. Права на
каталог должны быть ограничены пользователем, от которого работает приложение.

**Сессии живут в памяти.** Перезапуск приложения разлогинивает всех пользователей -
это нормально и не требует действий.
